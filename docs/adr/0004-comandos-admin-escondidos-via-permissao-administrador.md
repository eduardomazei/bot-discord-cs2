# Comandos admin escondidos via permissão nativa "Administrador", não via configuração manual por cargo

Os 12 comandos 100% administrativos (8 em `commands/_definicoes.js`, 4 modulares) agora usam `.setDefaultMemberPermissions(PermissionFlagsBits.Administrator)`, que faz o Discord parar de mostrar esses comandos na lista de quem não tem a permissão nativa "Administrador". `utils/permissions.js` (`CARGOS_ADM_IDS`, usado por `ehAdministrador()` pra decidir quem pode de fato *executar* um comando admin) passou a incluir os 4 cargos que já têm "Administrador" no servidor (Owner, Directors, Founders, 🕸️ Trupe), em vez de só Owner/Directors — mantendo visibilidade e permissão de execução alinhadas: quem vê um comando admin também consegue rodá-lo.

Consideramos o caminho mais preciso: `setDefaultMemberPermissions('0')` (ninguém por padrão) + configuração manual, por comando, em Configurações do Servidor → Integrações → Bot, liberando explicitamente só Owner/Directors. Rejeitamos essa opção porque exigiria ~12 configurações manuais na interface do Discord (fora do controle de versão, não reproduzível se o bot for reinstalado ou levado pra outro servidor) para resolver uma imprecisão pequena — e essa imprecisão já foi eliminada na prática ao incluir Founders/Trupe em `CARGOS_ADM_IDS`, já que essas eram justamente as únicas contas que veriam comandos que não conseguiam rodar.

`/presenca` ficou de fora dessa mudança: tem subcomandos abertos (`confirmar`/`cancelar`/`lista`) misturados com admin (`criar`/`finalizar`/`promover`), e o Discord não permite esconder subcomando individual — só o comando inteiro. Aplicar a permissão ali bloquearia `confirmar`/`cancelar`/`lista` pra todo mundo sem essa permissão.

Existe um cargo "Trupe" (sem o emoji 🕸️, 0 membros hoje) que também tem "Administrador" no servidor, mas foi deliberadamente deixado fora de `CARGOS_ADM_IDS`: incluir um cargo vazio hoje significa que qualquer promoção futura pra esse cargo específico ganharia acesso total ao bot sem necessariamente essa ser a intenção. Se alguém for promovido a esse cargo com intenção de ser admin do bot, `CARGOS_ADM_IDS` precisa ser atualizado manualmente.
